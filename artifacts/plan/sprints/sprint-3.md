# Sprint 3 — Go/Templ Renderer

## Objective

Implement the Go/Templ renderer — the primary code generation target. After this
sprint, `sigil generate --target go-templ` produces compilable Templ files, HTMX
interactions, CSS from theme tokens, and Go handler stubs.

## Context

**Read `docs/05_renderer-contract.md`** for the Renderer interface and output structure.

The Go/Templ renderer produces:
- `.templ` files for pages and shared components (Templ is a typed HTML templating language for Go)
- HTMX attributes for client-side interactivity (navigation, modals, forms)
- `theme.css` with CSS custom properties from theme tokens
- Go handler stubs for each DataSource

**Key dependency:** The Templ project (https://templ.guide). The generated `.templ`
files are source code that gets compiled by the `templ` CLI into Go code, which then
compiles into a Go binary. Sigil generates the `.templ` files — it does NOT run the
templ compiler.

## Tasks

### TASK-S3-001 | Priority A | Implement Renderer interface and engine

**Context:** The renderer engine orchestrates code generation. It receives a parsed
config, walks the component tree, and delegates to component-specific templates.

**What to do:**

Create `internal/renderer/renderer.go` with the `Renderer` interface from
`docs/05_renderer-contract.md`.

Create `internal/renderer/engine.go` — the orchestration layer:

```go
// Generate processes all pages and produces output files.
func Generate(cfg GenerateConfig) error {
    // 1. Load project config (.sigil/sigil.yaml)
    // 2. Load component registry
    // 3. Load and resolve theme
    // 4. Load datasource manifests
    // 5. For each page in .sigil/pages/:
    //    a. Parse and validate
    //    b. Build RenderContext
    //    c. Call renderer.Render(ctx)
    //    d. Collect OutputFiles
    // 6. Generate shared components (once)
    // 7. Generate theme CSS (once)
    // 8. Generate handler stubs (once per datasource)
    // 9. Write all OutputFiles to output directory
}
```

Add `sigil generate` command in `internal/cli/generate.go` with flags:
`--target`, `--output`, `--pages`, `--theme`, `--clean`, `--dry-run`

**Acceptance criteria:**
- [ ] `Renderer` interface defined
- [ ] Engine loads configs, builds render contexts, delegates to renderer
- [ ] `sigil generate --target go-templ --output out/ --dry-run` lists files that would be generated
- [ ] `--clean` removes output dir contents before generating
- [ ] Error handling: validation failures stop generation with clear messages

### TASK-S3-002 | Priority A | Page template generation (Go/Templ)

**Context:** For each page config, generate a `.templ` file that renders the component
tree. The templ file uses Go types and produces HTML with Tailwind classes and HTMX
attributes.

**What to do:**

Create `internal/renderer/gotempl/renderer.go` implementing the `Renderer` interface.

Create Go templates in `internal/renderer/gotempl/templates/` that generate `.templ` source code.

Example: for the sprint-dashboard page, generate:

```
// pages/sprint_dashboard.templ
// Generated by Sigil — do not edit manually
package pages

import "myproject/internal/ui/components"

templ SprintDashboard() {
    <div class="flex flex-col gap-4 p-6">
        <div class="flex justify-between items-center">
            <h2 class="text-xl font-semibold text-[rgb(var(--sigil-text))]">
                Sprint Dashboard
            </h2>
            @components.Button(components.ButtonProps{
                Label:   "New Sprint",
                Variant: "primary",
                Icon:    "plus",
                HxGet:   "/ui/modals/create-sprint",
                HxTarget: "#modal-container",
            })
        </div>
        @components.SearchBar(components.SearchBarProps{
            Placeholder: "Search sprints...",
            HxGet:       "/api/sprints",
            HxTarget:    "#table-sprints",
        })
        <div id="table-sprints">
            @components.DataTable(components.DataTableProps{
                // ... props from config
            })
        </div>
    </div>
}
```

**Component rendering strategy:**
- Walk the component tree depth-first
- For each component, look up its type and render the appropriate Templ call
- Layout types (rows, columns, grid) render as `<div>` with Tailwind flex/grid classes
- Primitive types render as Templ component calls
- Actions map to HTMX attributes (see `docs/05_renderer-contract.md`)

**Acceptance criteria:**
- [ ] Pages generate `.templ` files
- [ ] Component tree renders recursively
- [ ] Layout types produce correct Tailwind flex/grid classes
- [ ] Generated code is syntactically valid Templ
- [ ] File names are snake_case versions of page IDs

### TASK-S3-003 | Priority A | Shared component templates

**Context:** Shared components (Button, DataTable, SearchBar, etc.) are generated once
and imported by all page templates. They're reusable Templ components with typed props.

**What to do:**

Generate component `.templ` files for each component type used across pages:

For each component type, generate:
1. A props struct (`ButtonProps`, `DataTableProps`, etc.)
2. A templ component function
3. CSS classes using Sigil theme variables

Start with the most critical components:
- `button.templ` — with variant support via CSS classes
- `data_table.templ` — with HTMX-powered sort/filter/paginate
- `search_bar.templ` — with HTMX search triggering
- `modal.templ` — with HTMX modal loading
- `form.templ` — with HTMX form submission
- `heading.templ`, `text.templ`, `badge.templ`, `input.templ`, `select.templ`

**Acceptance criteria:**
- [ ] ~10 shared component `.templ` files generated
- [ ] Each has a typed props struct
- [ ] Components use `--sigil-*` CSS variables for theming
- [ ] HTMX attributes used for interactivity
- [ ] Page templates can import and call shared components

### TASK-S3-005 | Priority A | DataSource handler stub generation

**Context:** For each DataSource manifest, generate a Go handler file with stub
implementations. See `docs/05_renderer-contract.md` for the example.

**What to do:**

Create `internal/datasource/stubgen.go`:
- Read datasource manifest YAML
- Generate Go handler struct with List/Create/Read/Update/Delete methods
- Generate `RegisterRoutes()` method
- Generate request/response types based on fields
- Include TODO comments where developer fills in logic

**Acceptance criteria:**
- [ ] Handler stub generated for each datasource
- [ ] Methods match datasource capabilities (no Delete if not in capabilities)
- [ ] Route registration matches endpoint patterns
- [ ] Request structs have fields from datasource fields
- [ ] Generated Go code compiles (`go vet`)
